# Resslab Hub backend

FastAPI + SQLAlchemy 2.0 (async) + PostgreSQL 14. `make help` from this
folder lists every target. The dev server is `make dev` (or `make dev-backend`
at the root), on http://127.0.0.1:8000, docs at `/docs`. Alembic runs
`upgrade head` at every startup (`DATABASE_UPGRADE=false` to skip).

## Database migration

When a data dictionary changes in the data repo:

1. `make generate-model` regenerates the ORM models
   (`resslab_hub/models/database/*.py`) and the Pydantic schemas
   (`resslab_hub/models/api.py`). Both files are rewritten only between their
   `START_OF_GENERATED_CODE` / `END_OF_GENERATED_CODE` markers, the hand
   written parts around them stay. Read the diff.
2. `make database-revision name="what changed"` creates the Alembic revision.
   Check it, then `make database-upgrade` applies it.

The generator is `data/generate_model.py`, driven by `RESSLAB_DATA_DIR`
(default `../../resslab-hub-data`, a sibling of the repo).

```bash
make database-revision name="add foo column"   # new autogenerated revision
make database-upgrade                          # apply (also done at startup)
make database-downgrade                        # one revision back
```

## Upload data

Needs the data repo next to this one and the database up. See "Populate the
database" in the [root README](../README.md) for the clone and the Git LFS
note.

```bash
make upload-data          # everything, ~1 min
make upload-data REBUILD=1  # empty the data tables first, then everything
make upload-data-light    # one measurement file per series type, ~30 s
make upload-brace         # one component, see make help for the others
```

A plain upload updates the rows of each file and deletes the main rows that
left a main CSV, with their curves. It does not see a curve file that left the
repo. A rebuild (`REBUILD=1`, or `--rebuild`) empties the main tables of the
run and their curve tables, then uploads everything again. So nothing stays
from files that left the repo. It refuses to start when a main CSV is missing.
It also stops, and empties nothing, when another transaction holds the tables
for more than 30 s.

A file that fails does not stop the others. The uploader logs the error, and
at the end it logs one line per failed file and exits with code 1.

The uploader is a module of the package, so it also runs from the backend
image:

```bash
python -m resslab_hub.data.uploader all <path to resslab-hub-data>
python -m resslab_hub.data.uploader all <path> --series-limit 1   # the light variant
python -m resslab_hub.data.uploader all <path> --rebuild           # empty, then refill
python -m resslab_hub.data.uploader brace <path>/braces/steel_braces.csv --debug
```

The first argument is a type from the `Type` enum in
`resslab_hub/data/uploader.py` (`all`, `all-braces`, `brace`,
`brace-displacement`, `dictionary`, `readme`, ...). The flow is drawn in
[resslab_hub/data/uploader.md](resslab_hub/data/uploader.md).

### Upload data to a deployed environment (dev, stage, prod)

Do not tunnel and upload from your laptop. Two things keep the deployed
data up to date:

- On each push to `main`, the `upload.yml` workflow of the data repo sends
  the changed files to `POST /upload` (`type=all`, a tar of only those
  files). The hubs it sends to are in the repository variable
  `UPLOAD_TARGETS`, each with the name of the secret that holds its
  `API_PASSWORD`. The real repo sends to prod and stage, the test fork
  `EPFL-ENAC/resslab-hub-data-test` sends to dev. Without the variable, the
  workflow does nothing. `/upload` answers 200 when every file went in. It
  answers 422 with the list of failed paths when some failed (the good files
  are still written), and the workflow shows them as errors.
- Each night at 03:00 UTC, the CronJob `resslab-hub-upload-data-<env>` runs
  the upload with `--rebuild` from inside the cluster, next to the database.
  It cleans what the pushes miss: a deleted curve file, a failed push, a
  manual edit. It runs the backend image of the environment, on the CSV data
  image built from the `main` branch of the data repo (the test fork's image
  on dev). Only dev runs it each night for now (a patch in its overlay in
  `enack8s-app-config`). On stage and prod the CronJob stays suspended until
  they run a backend that knows `--rebuild`. To run it now, open the
  application of the environment in the ArgoCD UI, find the CronJob and use
  the `create-job` action. If a file fails, the job exits with code 1 and
  ArgoCD shows it as failed.

Two things to know:

- During a rebuild, the tables are empty or partly full for a few minutes.
  The site keeps serving, but a request in that window can see partial data.
  That is why the job runs at night.
- The backend caches responses per process for one hour, so the new data can
  take up to an hour to show. Restart the backend pods from ArgoCD if you need
  it right away.

Fallback if the cluster job is not an option (the data image is not built yet,
or you need to upload something that is not in the data repo): port-forward the
database and upload from your machine.

```bash
kubectl -n epfl-resslab-resslab-hub-dev port-forward svc/resslab-hub-db-dev 5434:5432
```

The local dev database already uses 5433 (see the root README), so the
example takes 5434. Set `POSTGRES_PORT` to the same value.

Set `secrets/.env` (at the **repo root**, not under `backend/`, the Makefile
loads `../secrets/.env`) with the creds from Infisical
(`/epfl-resslab/resslab-hub/db`, env slug `dev`, `staging` or `prod`):

```env
POSTGRES_HOST=localhost
POSTGRES_PORT=5434
POSTGRES_USER=<DB_USER>
POSTGRES_PASSWORD=<DB_PASSWORD>
API_PASSWORD=<any non-empty value>   # machine credential, see docs/auth.md
```

To send real sign-in mails instead of logging them, add the `SMTP_*` block
from `docs/auth.md`. Watch the quoting of `SMTP_USER`: double quotes turn the
backslash into a newline. To upload SEM images to the CDN, add the `S3_*`
block from `docs/sem-images.md`.

Then from `backend/`, run `make upload-data`. With `REBUILD=1`, it first empties the data tables it touches.

Finished upload jobs and their pods leave after a day (`ttlSecondsAfterFinished`).
Read the logs of a failed run before that.

## Backup and restore of a deployed database

Almost everything in the database comes from the data repo, so the upload job
can rebuild it. Only the `auth_*` tables live in the database alone: accounts,
linked identities, roles given by an admin, invitations, access requests and
sessions (see [docs/auth.md](../docs/auth.md)).

So the CronJob `resslab-hub-db-dump-<env>` dumps only these tables, each night
at 02:00 UTC. It writes `auth-<date>.dump` (`pg_dump -Fc`, a few kB) to the PVC
`resslab-hub-db-longtermbackup-pvc-<env>`, keeps 30 days of files, and fails
when `pg_dump` fails. The dump only locks the auth tables, so it can't block
the nightly rebuild at 03:00. The PVC name has `longtermbackup` in it, so the
team backup also copies it off the cluster (see "Build and deploy" in the team
wiki).

What a lost database without this dump would cost: every account and profile,
the roles and invitations an admin gave, the pending access requests, and all
sessions (everyone signed out). Roles from GitHub, `ADMIN_EMAILS` and academic
emails come back at the next sign-in. Who submitted what stays in the commit
trailers of the data repo.

To restore a database (example on prod):

1. Start from an empty database. The backend runs the migrations when it
   starts.
2. Load the data: in ArgoCD, run `create-job` on the CronJob
   `resslab-hub-upload-data-prod`.
3. Open a shell next to the dump files:

   ```bash
   NS=epfl-resslab-resslab-hub-prod
   kubectl -n $NS run auth-restore --rm -it --restart=Never --image=postgres:14 \
     --overrides='{"spec":{"containers":[{"name":"auth-restore","image":"postgres:14",
       "stdin":true,"tty":true,"command":["bash"],
       "envFrom":[{"secretRef":{"name":"db-secret"}}],
       "volumeMounts":[{"name":"backup","mountPath":"/backup"}]}],
       "volumes":[{"name":"backup","persistentVolumeClaim":
         {"claimName":"resslab-hub-db-longtermbackup-pvc-prod"}}]}}'
   ```

4. In that shell, restore the rows of the newest dump:

   ```bash
   ls -lt /backup
   export PGHOST=resslab-hub-db-prod PGDATABASE=postgres PGUSER=$DB_USER PGPASSWORD=$DB_PASSWORD
   pg_restore --data-only --single-transaction /backup/auth-<date>.dump
   ```

   The auth tables must be empty. If someone signed in after the crash, remove
   their rows first: on a duplicate key the restore stops and changes nothing.
   The dump also holds the table definitions (`pg_restore -l` lists them), so you
   can compare the columns with the current migration if the restore complains.

For a full dump by hand (before a risky migration, for example), run `pg_dump`
in the database pod and keep the file on your machine:

```bash
kubectl -n epfl-resslab-resslab-hub-prod exec resslab-hub-db-prod-0 -- \
  sh -c 'pg_dump -U "$POSTGRES_USER" -Fc postgres' > prod-$(date +%F).dump
```

## Validate a component folder

With the backend running, `make validate-braces` (or any type listed by
`make validate-data`) tars that folder of the data repo and posts it to
`/validate` with the machine credential. Same check the data repo CI runs.
