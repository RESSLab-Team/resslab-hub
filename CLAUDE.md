# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

RESSLab-Hub is a fullstack research database for structural steel components (braces, columns, connections, materials, residual stresses, HSS columns, EBF links). The backend exposes a REST API; the frontend is a Vue 3 SPA with data visualization tools.

**Prerequisites**: [uv](https://docs.astral.sh/uv/) (manages Python automatically), Node.js ≥ 18 (CI uses the current LTS), Docker with the Compose v2 plugin, Make.

## Commands

### Root-level (from the repo root)

```bash
make install          # Install all dependencies (npm + uv sync + frontend)
make dev-all          # database + frontend (new tab) + backend together
make dev-database     # Start PostgreSQL via Docker Compose
make dev-backend      # Start FastAPI backend (http://127.0.0.1:8000)
make dev-frontend     # Start Vite dev server (http://127.0.0.1:5173)
make test             # Run both backend (pytest) and frontend (vitest) tests
make lint             # Lint both backend (pre-commit) and frontend (ESLint)
make api              # Regenerate openapi.json + frontend/src/backend/
make upload-data      # Upload all CSV data to local database (erases existing)
make sample-data      # Generate synthetic contribution batches into sample-data/
```

Also available (see the root `Makefile`): `test-cov`, `benchmark`, `update`, `run` (Docker build + start all services with 7 backend replicas), `upload-data-test` (targets the test deployment via `ENV_FOR_DYNACONF=test`), `backup-dump DEST_FOLDER=path`.

### Backend (from `backend/`)

```bash
uv run pytest                                    # Run all tests
uv run pytest tests/test_foo.py                  # Run a single test file
uv run pytest tests/test_foo.py::test_bar        # Run a single test
uv run pre-commit run --all-files                # Lint (black, flake8, isort)
make database-upgrade                            # Apply Alembic migrations
make database-downgrade                          # Roll back one revision
make database-revision name="description"        # Create new autogenerated migration
make generate-model                              # Regenerate ORM models from CSV data dictionaries
make transform-data                              # Regenerate frontend assets/ section CSVs from data repo
make sample-data EXPERIMENTS=15 OUTLIERS=3       # Synthetic contribution batches (reads the DB for in-range values)
DRY_RUN=1 make precompute-sem                    # Convert SEM TIFs to WebP + dimple JSONs locally (no CDN upload)
make precompute-sem                              # Same, but uploads to EPFL enacit4r-cdn (needs ACCESS_KEY_ID + ACCESS_KEY_SECRET)
```

Per-component upload targets (`make upload-brace`, `upload-column`, `upload-connection`, `upload-material`, `upload-tensile-coupon`, `upload-ductile-fracture`, `upload-residual-stress`, `upload-hss-column`, `upload-eccentric-braced-frame`) and validation targets (`make validate-braces`, `validate-columns`, … — POST a tar of component data to the `/validate` endpoint) are listed in `backend/Makefile`.

Backend dev server requires `secrets/.env` with at minimum `POSTGRES_PASSWORD=changeit`. The Makefile sets `DOTENV_PATH_FOR_DYNACONF` automatically. Alembic `upgrade head` runs automatically at backend startup (set `DATABASE_UPGRADE=false` to skip, e.g. when running `make api`).

To upload data to production, first open an SSH tunnel: `ssh -NL 5432:localhost:5432 root@resslab-hub.epfl.ch`, then point `secrets/.env` at the prod credentials and run `make upload-data`.

### Dev server (worktrees)

After you make frontend changes, keep a Vite dev server running for the current
worktree and tell me the URL — don't make me cd in and start it myself.

1. Run it from the worktree's own `frontend/` directory. Worktrees have
   `node_modules` symlinked, so `npm run dev` works with no fresh install.
2. First check whether one is already serving this worktree — a background task
   you started in an earlier turn, or `pgrep -af vite | grep <worktree path>`.
   If so, reuse it; don't spawn a second server.
3. Otherwise start it in the background on a per-worktree port so parallel
   worktrees don't collide:
   `npm run dev -- --port <PORT>` where `<PORT>` = 5173 + a small offset derived
   from the worktree name (main checkout = 5173). Vite falls back to the next
   free port if it's taken.
4. Data-backed pages need the backend too (`make dev-backend` + `make
   dev-database`); it's read from `VITE_APP_BACKEND_URL` (http://127.0.0.1:8000
   in `.env.development`). Pure UI/layout changes render without it.
5. At the end of your response, print the actual URL Vite bound to (read it from
   the server log), e.g. http://localhost:5175/

## Architecture

### Backend (`backend/resslab_hub/`)

FastAPI + SQLAlchemy 2.0 async + PostgreSQL. Key files:

- `main.py` — app setup, router registration, CORS, middleware
- `config.py` — Dynaconf settings with required keys (`POSTGRES_PASSWORD`, `API_PASSWORD`)
- `models/api.py` — Pydantic schemas (auto-generated, do not edit manually)
- `models/database/` — SQLAlchemy ORM models (auto-generated from CSV data dictionaries)
- `routers/` — one file per component type (braces, columns, connections, materials [cyclic coupons], tensile_coupon, ductile_fracture, residual_stress, hss_columns, eccentric_braced_frame) plus `analytics.py` and `root.py`
- `data/generate_model.py` — reads CSV data dictionaries from `resslab-hub-data` repo and generates both ORM models and Pydantic schemas

**Model generation workflow**: When the data schema changes, run `make generate-model` (requires the sibling `resslab-hub-data` repo, resolved as `../../resslab-hub-data` from `backend/`), then create an Alembic migration with `make database-revision`.

### Frontend (`frontend/src/`)

Vue 3 + TypeScript + Vite + Vuetify 3 + Pinia.

- `backend/` — auto-generated TypeScript API client (from `openapi.json` via `make api`); never edit manually
- `views/` — page-level components, named `{Type}View.vue` (overview), `{Type}Database.vue` (data table), `{Type}ModelView.vue` (model curves)
- `components/` — reusable components, organized by domain (`braces/`, `columns/`, etc.) plus `commons/`
- `composables/` — Vue 3 composition functions
- `stores/` — Pinia stores
- `locales/` — i18n translation files
- `assets/` — static CSV section tables used for component selection

**Frontend API client**: When the backend API changes, run `make api` from the root to regenerate `frontend/src/backend/`.

### Infrastructure

- **Reverse proxy**: Traefik v3.6 routes `/` → frontend, `/api` → backend (stripping the `/api` prefix). In dev the backend listens directly on `:8000` with no prefix; in prod code paths must tolerate `ROOT_PATH=/api`.
- **Database**: PostgreSQL 14 (Alpine)
- **Secrets**: `secrets/.env` (gitignored) — not committed; create with `mkdir -p secrets && echo POSTGRES_PASSWORD=changeit > secrets/.env`. Backend also requires `API_PASSWORD` for the `/validate` and admin endpoints.
- **Branch model**: `dev` is the default/integration branch (deploys to the k8s `dev` overlay); `stage` is the single pre-prod branch (k8s `stage` overlay); `main` is the release branch — `release-please.yml` cuts version tags (`v*.*.*`) from it, and tag pushes deploy to the k8s `prod` overlay. Promote `dev` → `stage` → release via PRs/tags.
- **CI/CD**: GitHub Actions — `ci.yml` runs tests/lint on push/PR to `dev` + `main`; `release-please.yml` auto-manages versioning on `main`; `deploy.yml` builds + deploys (`dev`/`stage` branches → k8s, `v*.*.*` tags → prod) via the EPFL enac build-push-deploy action. The legacy `deploy-test.yml` / `deploy-prod.yml` (old enac-deploy-action) were removed once the k8s migration (#227) fully replaced them.

## resslab-hub-data Repository

Contains all raw experimental data and the data dictionaries that drive schema generation.

### Structure

Each component type has its own directory with a main CSV and a data dictionary. The material family (cyclic coupons, tensile coupons, ductile fracture) is nested under a shared `material/` parent to mirror the frontend's Materials tab:

| Component | Directory | Main CSV | Data Dictionary |
|-----------|-----------|----------|-----------------|
| Braces | `braces/` | `steel_braces.csv` | `steel_braces_data_dictionary.csv` |
| Columns | `columns/` | `steel_columns.csv` | `steel_columns_data_dictionary.csv` |
| Connections | `connections/` | `connections.csv` | `connections_data_dictionary.csv` |
| HSS Columns | `hss_columns/` | `hss_columns.csv` | `hss_columns_data_dictionary.csv` |
| EBF | `eccentric_braced_frames/` | `eccentric_braced_frames.csv` | `eccentric_braced_frames_data_dictionary.csv` |
| Cyclic Coupons | `material/cyclic_coupons/` | `steel_material.csv` | `steel_material_data_dictionary.csv` |
| Tensile Coupons | `material/tensile_coupons/` | `tensile_coupons.csv` | `tensile_coupons_data_dictionary.csv` |
| Ductile Fracture | `material/ductile_fracture/` | `ductile_fracture.csv` | `ductile_fracture_data_dictionary.csv` |
| Residual Stresses | `residual_stresses/` | `residual_stresses.csv` | `residual_stresses_data_dictionary.csv` |

Time-series test data (force-displacement, moment-rotation, stress-strain curves) lives in subdirectories: `force_displacement/`, `moment_rotation_strong/`, `moment_rotation_weak/`, `axial_shortening_rotation/`, `Panel_zone/`, `Global/`, `stress_strain/`, etc.

### Data Dictionary Format

Each `*_data_dictionary.csv` has 7 columns that drive `generate_model.py` to produce SQLAlchemy models and Pydantic schemas:

```
column_name, description, symbol, unit, type, example_value, nullable
```

- **type** values: `Numeric`, `DecimalFloat`, `SmallInteger`, `BigInteger`, `Integer`, `String`, `Date`, `Boolean`
- **nullable**: `True`/`False`
- **symbol**: markdown-formatted symbol (used in frontend display)
- **unit**: SI unit string or `-` if unitless

### Data CI/CD

The data repo has its own GitHub Actions (`.github/workflows/data-validation.yml`) that validate PRs before merging. The `main` branch feeds production (`resslab-hub.epfl.ch`), `test` branch feeds the test deployment. Data contributors fork, branch, submit a PR, and data is validated automatically before upload. **Squash-merge is mandatory** — the CI only re-validates `HEAD~1..HEAD` on `main`, so non-squashed merges make post-merge validation useless.

**Gotcha:** the validation workflow has a hardcoded `filters:` list (around lines 27–33 of `data-validation.yml`) mapping directory globs to validation job names. EBF was never added to that list, so EBF PRs bypass validation silently. When adding a new component type, add both the directory and an entry like `new-things: 'new_things/**'`. The filter key must match the backend uploader `Type` enum (`all-new-things` → filter key `new-things`) — mismatches silently skip validation rather than erroring.

### SEM (ductile-fracture) local dev

SEM images live on the EPFL enacit4r-cdn in prod. For local dev:

1. Run `cd backend && DRY_RUN=1 make precompute-sem` — converts every TIF under `resslab-hub-data/material/ductile_fracture/sem/<id>/` to WebP and writes dimple JSONs alongside, output goes to `resslab-hub-data/material/ductile_fracture/sem/_webp/` (gitignored).
2. Create the symlink **once**: `ln -s ../../../resslab-hub-data/material/ductile_fracture/sem/_webp frontend/public/sem`. It's gitignored (it would be a dangling link inside the Docker build context and break the prod build). Vite serves the files at `/sem/<id>/...`. `.env.development` already sets `VITE_SEM_CDN_BASE_URL=/sem`, so `npm run dev` hits the local files. Production builds use `.env.production` → the real CDN.

For real CDN uploads, drop `DRY_RUN` and provide `ACCESS_KEY_ID` / `ACCESS_KEY_SECRET` from EPFL ops. The script then sets `has_sem=yes` in `ductile_fracture.csv` for the processed specimens (set-only, never clears) — commit that change to the data repo.

### Adding a new component tab

See `docs/adding-a-new-tab.md` for the exhaustive end-to-end playbook (data repo → backend codegen/router/uploader/migration → OpenAPI regen → frontend views/components/charts/utils/i18n/map/home + gotchas from EBF's post-launch feedback). Other maintenance notes live in `docs/` (e.g. `modernization-followups.md`).

**Adding a column to a data dictionary** also means giving it a scientific category, which is what the collapsible groups in the filter rail, the contribution editor, the curation review panel and the specimen drawer are built from. The taxonomy is `frontend/src/utils/fieldGroups.ts` and the review tables are `docs/variable-categories.md`. Most new columns are matched by an existing pattern (`uvc_*`, `pid_*`, `chemical_composition_*`, `_100fit`) and need no edit; anything unmatched lands in `other` and fails `fieldGroups.spec.ts`, which reads the real column list out of the `sample-data/` CSV headers.

## Conventions

- **Git hooks**: [Lefthook](https://lefthook.dev) orchestrates `commit-msg` / `pre-commit` / `pre-push`. Config in `lefthook.yml` at the repo root; installed automatically by `make install` (or `make hooks`). Escape hatch: `LEFTHOOK=0 git commit ...`.
- **Commits**: Conventional Commits enforced by commitlint on `commit-msg`; Release Please auto-manages versioning.
- **Python formatting**: black + isort + flake8 via the Python `pre-commit` framework (`backend/.pre-commit-config.yaml`) — staged files at commit time, all files at push time and in CI.
- **Frontend formatting**: ESLint (Vue3 + TS + Prettier) + Prettier on staged files at commit time. `vue-tsc` type-check at push time and in CI.
- **TypeScript**: strict mode; Prettier for formatting.
