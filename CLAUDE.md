# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

RESSLab-Hub is a fullstack research database for structural steel components (braces, columns, connections, materials, residual stresses, HSS columns, EBF links). The backend exposes a REST API; the frontend is a Vue 3 SPA with data visualization tools.

**Prerequisites**: [uv](https://docs.astral.sh/uv/) (manages Python automatically), Node.js ≥ 18 (CI uses the current LTS) with [pnpm](https://pnpm.io) 11 (`npm install -g pnpm`), Docker with the Compose v2 plugin, Make.

## Commands

### Root-level (from the repo root)

```bash
make install          # Install all dependencies (pnpm + uv sync + frontend)
make dev-all          # database + backend + frontend in the current terminal
make tmux-dev-all     # same, as a tmux session with a claude pane and a shell pane
make dev-database     # Start PostgreSQL via Docker Compose
make dev-backend      # Start FastAPI backend (http://127.0.0.1:8000)
make dev-frontend     # Start Vite dev server (http://127.0.0.1:5173)
make test             # Run both backend (pytest) and frontend (vitest) tests
make lint             # Lint both backend (pre-commit) and frontend (ESLint)
make api              # Regenerate openapi.json + database-columns.json + frontend/src/backend/
make upload-data      # Upload all CSV data to local database (erases existing)
make sample-data      # Generate synthetic contribution batches into sample-data/
```

Also available (see the root `Makefile`): `test-cov`, `benchmark`, `update`, `run` (Docker build + start all services with 7 backend replicas), `backup-dump DEST_FOLDER=path`.

### Backend (from `backend/`)

```bash
uv run pytest                                    # Run all tests
uv run pytest tests/test_foo.py                  # Run a single test file
uv run pytest tests/test_foo.py::test_bar        # Run a single test
uv run pre-commit run --all-files                # Lint (ruff + ruff-format)
make database-upgrade                            # Apply Alembic migrations
make database-downgrade                          # Roll back one revision
make database-revision name="description"        # Create new autogenerated migration
make generate-model                              # Regenerate ORM models from CSV data dictionaries
make transform-data                              # Regenerate frontend assets/ section CSVs from data repo
make sample-data EXPERIMENTS=15 OUTLIERS=3       # Test batches from real DB records and data repo curves, self-checked
DRY_RUN=1 make precompute-sem                    # Convert SEM TIFs to WebP + dimple JSONs locally (no CDN upload)
make precompute-sem                              # Same, but also uploads to EPFL enacit4r-cdn (needs the S3_* settings in secrets/.env)
make precompute-fracture-figures                 # Redraw the committed per-specimen ductile-fracture geometry SVGs
```

Per-component upload targets (`make upload-brace`, `upload-column`, `upload-connection`, `upload-material`, `upload-tensile-coupon`, `upload-ductile-fracture`, `upload-residual-stress`, `upload-hss-column`, `upload-eccentric-braced-frame`) and validation targets (`make validate-braces`, `validate-columns`, …: tar one folder of the data repo and POST it to `/validate` with the machine credential, backend must be running) are listed in `backend/Makefile`. `make help` (root, `backend/`, `frontend/`) prints every target with a one-line description.

Backend dev server requires `secrets/.env` with at minimum `POSTGRES_PASSWORD=changeit`. The Makefile sets `DOTENV_PATH_FOR_DYNACONF` automatically. Alembic `upgrade head` runs automatically at backend startup (set `DATABASE_UPGRADE=false` to skip, e.g. when running `make api`).

The uploader lives in the package (`resslab_hub/data/uploader.py`) and runs as `python -m resslab_hub.data.uploader <type> <files>`, so the backend image can upload too. That is how deployed environments stay up to date: on each push to `main`, the data repo's `upload.yml` posts the changed files to `/upload` (200, or 422 with the failed paths) of each hub in its `UPLOAD_TARGETS` repository variable (real repo: prod and stage, test fork: dev), and each environment has a CronJob `resslab-hub-upload-data-<env>` (manifests in `enack8s-app-config`) that runs `--rebuild` (empty the data tables, upload everything again) to clean what the pushes miss. Only dev runs it nightly so far (03:00 UTC, patched in its overlay); stage and prod keep it suspended until their backend knows `--rebuild`. It can also be triggered by hand from the ArgoCD UI with the `create-job` action. It runs the environment's own backend image against a CSV data image built by the data repo, in-cluster, with no tunnel, and exits 1 when a file failed. The backend caches responses for an hour per process, so restart the backend pods if the new data must show immediately. Uploading from a laptop over a port-forward still works as a fallback (see `backend/README.md`).

### Dev servers and worktrees

Every branch gets its own git worktree, tmux session `resslab-hub/<branch>` and agent, managed by [wtx](https://github.com/EPFL-ENAC/wtx) from `wtx.toml`. The panes are `agent` (the left half), then `backend`, `frontend` and `shell` stacked on the right. A human starts one with `wtx go feat/x` and closes it with `wtx done feat/x`. wtx does the ports, deps, agent settings, push guard and session; its `post_setup` hook runs `scripts/wt-setup.sh --wtx` for what is ours (seeding `secrets/.env` and `sample-data/`, the branch database, the DB keys in `secrets/.env`), and `pre_teardown` runs `scripts/wt-teardown.sh` to drop that database. Full guide: `docs/worktree-dev-environment.md` (it still describes the older script-only flow for the parts wtx took over).

- **Know where you are**: you are in a worktree exactly when `.env.worktree` exists at the repo root (your path contains `.claude/worktrees/`). Every pane exports it, so `echo $WT_BRANCH $BACKEND_PORT $FRONTEND_PORT $DB_NAME` orients you. In a shell without them, `set -a; . .env.worktree; set +a` first.
- **Ports**: per worktree, in `.env.worktree`. The main checkout uses 8000/5173. Never hardcode a port, never guess, never start a second server on a port already served.
- **Reuse before starting**: the dev servers already run in their panes. Do not start them again. Read `.wt-logs/backend.log` and `.wt-logs/frontend.log` to see what they do (the tmux socket is outside your sandbox, `tmux` commands fail).
- **Reaching the servers**: `wtx curl <backend|frontend> [path] [curl args]` fills in this worktree's port and never prompts, whatever the method: `wtx curl backend /healthz`. Plain read-only `curl` to your own localhost ports also works.
- **Finish** a frontend or backend change by printing its URL: `http://localhost:$FRONTEND_PORT/` or `http://127.0.0.1:$BACKEND_PORT/docs`. Use the app through the Vite port only: it proxies `/api` to the backend (`vite.config.ts`), which is what makes the session cookie first-party.
- `sample-data/` arrives seeded from the main checkout (the contribution flow's test batches); regenerate with `make sample-data` if needed.

#### Working in a worktree — rules

- **You own exactly one branch**: the worktree's. Commit and push to it freely. Never push `dev`, `stage` or `main`, never push another branch, never force-push, never create or push tags (`deploy.yml` deploys prod on `v*.*.*`, release-please owns tags). A pre-push hook and the session's deny rules refuse it: that is the design, not a bug to work around. When the work is ready, say so; a human lands it with `wtx land <branch>` from the main checkout.
- **Directories outside this repo**: `resslab-hub-data` (`../resslab-hub-data`) is `pair`, the k8s config (`~/code/enack8s-app-config/epfl-resslab/resslab-hub`) is `read`. Read them freely. You may not write in a `read` directory, and a `pair` one is writable only through a paired worktree: to get one, a human runs `wtx go <branch> --with resslab-hub-data=<branch>`, and the change lands through that repo's own pull request.
- **The database**: each worktree gets its own throwaway `resslab_hub_<slug>` on `localhost:5433`, cloned at setup from the ~20 MB `resslab_hub_light` template (every main table, dictionary and README; one measurement file per series type), with migrations ON — migrate, upload, or break it freely, and `make db-branch` re-clones it (wtx setup does it for you). The login in `secrets/.env` is the clone's own role `wt_<slug>`, which owns that database and cannot connect to any other one, so do not edit `POSTGRES_DB` or `POSTGRES_USER` there. Check `DB_NAME` in `.env.worktree`: if it still says `postgres`, the light template didn't exist at setup and you are on the **shared 3.4 GB dev dataset** — then never run `alembic upgrade`/`downgrade`, `make database-upgrade` or `make upload-data` (the shared DB runs with `DATABASE_UPGRADE=false`; ask the user to run `make db-template-light` once, then `make db-branch`). `make db-branch-full` clones the full 3.4 GB `resslab_hub_template` when a branch needs real data volumes; `make db-branch-drop` returns to the shared DB.
- **Contributions**: `secrets/.env` points `DATA_REPO` at the test fork `EPFL-ENAC/resslab-hub-data-test` (seeded by `wt-setup.sh` with its own App installation id), so a local submission never opens a pull request on the real data repo. Check it before testing the pipeline; `make data-fork-reset` re-syncs the fork's `main` (`docs/contributing-data.md`).
- **Tests**: `pytest` reads `POSTGRES_TEST_DB` from `.env.worktree` (a per-worktree throwaway database) so parallel worktrees don't drop each other's test DB — keep it exported. The sandbox has no `localhost`, so `make test` runs pytest through `scripts/with-db.py`: it listens on `localhost:5433` inside the sandbox and tunnels each connection through the sandbox proxy, which allows `localhost:5433` (`allowed_domains` in `wtx.toml`). Any other command that needs the DB works the same way: `python3 scripts/with-db.py uv run …` (from `backend/`, `python3 ../scripts/with-db.py …`). Outside the sandbox it just runs the command. The login in `secrets/.env` still decides which database you reach.
- **Network**: read the web freely. Anything that writes outward (`curl -X POST`, `gh pr create`, …) or runs downloaded code (`curl … | sh`, `pnpm dlx …`) prompts the user by design; don't work around a prompt.

## Architecture

### Backend (`backend/resslab_hub/`)

FastAPI + SQLAlchemy 2.0 async + PostgreSQL. Key files:

- `main.py`: app setup, router registration, middleware (response cache, gzip, CSRF)
- `config.py`: Dynaconf settings with required keys (`POSTGRES_PASSWORD`, `API_PASSWORD`)
- `models/api.py`: Pydantic schemas (auto-generated, do not edit manually)
- `models/database/`: SQLAlchemy ORM models (auto-generated from CSV data dictionaries)
- `routers/`: one file per component type (braces, columns, connections, materials [cyclic coupons], tensile_coupon, ductile_fracture, residual_stress, hss_columns, eccentric_braced_frame) plus `root.py` (`/validate`, `/upload`, health), `auth.py`, `contributions.py` (submit and edit, see `docs/contributing-data.md`), `curation.py` (the review queue, `docs/curation.md`), `admin.py` (members, invitations and access requests, `docs/auth.md`), `dictionary.py` (data dictionaries and READMEs) and `analytics.py` (Google Analytics counts)
- `contributions/`: how a submission becomes a branch and pull request on the data repo: `github.py` (githubkit client, one shared HTTP client per process), `submission.py`, `projection.py`, `trailers.py` (provenance as commit trailers)
- `utils/caching.py` and `utils/warmup.py`: the per-process response cache (ETag on a data version, `CACHE_MAX_AGE`, bumped by `/upload`) and the startup warmup that fills it; `docs/dashboard-architecture.md`
- `auth/`: sign-in, sessions and roles (#247, #248). `roles.py` works out a role (GitHub permission on the data repo first, `github_sync.py` keeps it fresh), `access.py` handles invitations and access requests. `deps.py` holds the FastAPI dependencies (`require_user`, `require_role`, and the machine-credential ones); see `docs/auth.md`
- `data/generate_model.py`: reads CSV data dictionaries from `resslab-hub-data` repo and generates both ORM models and Pydantic schemas

**Model generation workflow**: When the data schema changes, run `make generate-model` (requires the `resslab-hub-data` repo; `backend/Makefile` finds it through `RESSLAB_DATA_DIR`, default `../../resslab-hub-data`, which worktrees export as an absolute path from `.env.worktree`), then create an Alembic migration with `make database-revision`.

### Frontend (`frontend/src/`)

Vue 3 + TypeScript + Vite + Vuetify 3 + Pinia.

- `backend/`: auto-generated TypeScript API client (from `openapi.json` via `make api`); never edit manually
- `views/`: page-level components. Per database: `{Type}View.vue` (overview), `{Type}Database.vue` (data table), `{Type}ModelView.vue` (model curves), `{Type}FragilityCurve.vue` (braces, columns, connections); tensile coupons and ductile fracture only have a `Database` view (sub-tabs of Materials). Plus the pages: `HomeView`, `AboutView`, `LoginView`, `LoginVerifyView`, `AccountView`, `ForbiddenView`, `AdminView`, `ContributeView`, `CurationQueueView`, `CurationReviewView`
- `components/`: reusable components, organized by domain (`braces/`, `columns/`, etc.) plus `commons/`
- `composables/`: Vue 3 composition functions
- `stores/`: Pinia stores
- `locales/`: i18n translation files
- `assets/`: static CSV section tables used for component selection

**Frontend API client**: When the backend API changes, run `make api` from the root to regenerate `frontend/src/backend/`.

### Infrastructure

- **Reverse proxy**: Traefik v3.6 routes `/` → frontend, `/api` → backend (stripping the `/api` prefix). In dev the backend listens directly on `:8000` with no prefix; in prod code paths must tolerate `ROOT_PATH=/api`.
- **Database**: PostgreSQL 14 (Alpine)
- **Secrets**: `secrets/.env` (gitignored) — not committed; create with `mkdir -p secrets && echo POSTGRES_PASSWORD=changeit > secrets/.env`. `API_PASSWORD` is the machine credential: it guards `/upload` and `/user`, and is one of the two ways into `/validate` (the other is a signed-in account). When `DEPLOYMENT` is set, the API refuses to start on a missing, `changeit` or short `API_PASSWORD`, or an empty `POSTGRES_PASSWORD` (`refuse_default_secrets` in `config.py`). People sign in with a session cookie instead — see `docs/auth.md` for the sign-in setup (`PUBLIC_BASE_URL`, `GITHUB_OAUTH_*`, `SMTP_*`, `ADMIN_EMAILS`, `CONTRIBUTOR_DOMAINS`). `CONTRIBUTIONS_ENABLED=false` switches the whole contribution pipeline off at runtime (backend 404, frontend hides it through `GET /features`); prod keeps it off until release, see `docs/releasing.md`.
- **Branch model**: `dev` is the default/integration branch (deploys to the k8s `dev` overlay); `stage` is the single pre-prod branch (k8s `stage` overlay); `main` is the release branch — `release-please.yml` cuts version tags (`v*.*.*`) from it, and tag pushes deploy to the k8s `prod` overlay. Promote `dev` → `stage` → release via PRs/tags. Promotion PRs must be merged with a **merge commit**, never squashed, or Release Please sees nothing to release. Full steps: `docs/releasing.md`.
- **CI/CD**: GitHub Actions — `ci.yml` runs tests/lint on push/PR to `dev`, `stage` and `main`; `release-please.yml` auto-manages versioning on `main`; `deploy.yml` builds + deploys (`dev`/`stage` branches → k8s, `v*.*.*` tags → prod) via the EPFL enac build-push-deploy action. The legacy `deploy-test.yml` / `deploy-prod.yml` (old enac-deploy-action) were removed once the k8s migration (#227) fully replaced them.

### Related Repositories

- `resslab-hub-data`: CSV data files and data dictionaries that drive schema generation. `backend/Makefile` reaches it through `RESSLAB_DATA_DIR` (default `../../resslab-hub-data`, i.e. a sibling of the main checkout); git worktrees live deeper in the tree, so `scripts/wt-setup.sh` writes the absolute path into their `.env.worktree`. - `resslab-hub-scripts`: MATLAB scripts for component models and fragility curves

## resslab-hub-data Repository

Contains all raw experimental data and the data dictionaries that drive schema generation.

### Structure

Each component type has its own directory with a main CSV and a data dictionary. The material family (cyclic coupons, tensile coupons, ductile fracture) is nested under a shared `material/` parent to mirror the frontend's Materials tab:

| Component         | Directory                    | Main CSV                      | Data Dictionary                               |
| ----------------- | ---------------------------- | ----------------------------- | --------------------------------------------- |
| Braces            | `braces/`                    | `steel_braces.csv`            | `steel_braces_data_dictionary.csv`            |
| Columns           | `columns/`                   | `steel_columns.csv`           | `steel_columns_data_dictionary.csv`           |
| Connections       | `connections/`               | `connections.csv`             | `connections_data_dictionary.csv`             |
| HSS Columns       | `hss_columns/`               | `hss_columns.csv`             | `hss_columns_data_dictionary.csv`             |
| EBF               | `eccentric_braced_frames/`   | `eccentric_braced_frames.csv` | `eccentric_braced_frames_data_dictionary.csv` |
| Cyclic Coupons    | `material/cyclic_coupons/`   | `steel_material.csv`          | `steel_material_data_dictionary.csv`          |
| Tensile Coupons   | `material/tensile_coupons/`  | `tensile_coupons.csv`         | `tensile_coupons_data_dictionary.csv`         |
| Ductile Fracture  | `material/ductile_fracture/` | `ductile_fracture.csv`        | `ductile_fracture_data_dictionary.csv`        |
| Residual Stresses | `residual_stresses/`         | `residual_stresses.csv`       | `residual_stresses_data_dictionary.csv`       |

Two more top-level folders: `contributions/` (per-submission JSON records from before provenance moved to commit trailers; the curation code still reads them for old pull requests) and `sample-data/` (an older, single-record copy of the synthetic batches this repo generates with `make sample-data`).

Each directory also carries a `README.md` written for contributors (identifier convention, expected response files with exact headers and units, how to submit); it is uploaded with the data (`Type.README` in `uploader.py`, folder-to-database map `README_DATABASES`) and rendered in the hub's submission form next to the dictionary table, so keep it in step with the uploader/validator when a folder or header changes. Do not duplicate the data dictionary inside it.

Time-series test data (force-displacement, moment-rotation, stress-strain curves) lives in subdirectories: `force_displacement/`, `moment_rotation_strong/`, `moment_rotation_weak/`, `axial_shortening_rotation/`, `Panel_zone/`, `Global/`, `stress_strain/`, etc.

### Data Dictionary Format

Each `*_data_dictionary.csv` has 8 columns. The first 7 drive `generate_model.py` to produce SQLAlchemy models and Pydantic schemas; `group` is read by the uploader and served by `GET /dictionary`:

```
column_name, description, symbol, unit, type, example_value, nullable, group
```

- **type** values: `Numeric`, `DecimalFloat`, `SmallInteger`, `BigInteger`, `Integer`, `String`, `Date`, `Boolean`
- **nullable**: `True`/`False`
- **symbol**: markdown-formatted symbol (used in frontend display)
- **unit**: SI unit string or `-` if unitless
- **group**: the scientific category, one of the names in `docs/variable-categories.md`

### Data CI/CD

The data repo has its own GitHub Actions (`.github/workflows/data-validation.yml`) that validate PRs before merging. The `main` branch feeds every deployment: it builds the `resslab-hub-data:main` image that each environment's upload CronJob reads, and submissions from dev, stage and laptops all open their pull request into it (close those, never merge them). There is no other long-lived branch, `test` was deleted. Data contributors fork, branch, submit a PR, and data is validated automatically before upload. **Squash-merge is mandatory** — the CI only re-validates `HEAD~1..HEAD` on `main`, so non-squashed merges make post-merge validation useless.

**Gotcha:** the validation workflow has a hardcoded `filters:` list in `data-validation.yml` mapping directory globs to validation job names, and a folder missing from it is never validated, with no error (EBF shipped like that for a while). When adding a new component type, add both the directory and an entry like `new-things: 'new_things/**'`. The filter key must match the backend uploader `Type` enum (`all-new-things` → filter key `new-things`) — mismatches silently skip validation rather than erroring. The workflow also has a `line-endings` job (LF + final newline on every CSV).

### SEM (ductile-fracture) local dev

Full guide: `docs/sem-images.md` (file names, what the script computes, the CDN variables, adding images). SEM images live on the EPFL enacit4r-cdn in prod. For local dev:

1. Run `cd backend && DRY_RUN=1 make precompute-sem` — converts every TIF under `resslab-hub-data/material/ductile_fracture/sem/<id>/` to WebP and writes dimple JSONs alongside, output goes to `resslab-hub-data/material/ductile_fracture/sem/_webp/` (gitignored). Real runs write that folder too, then upload it. The code is `backend/resslab_hub/sem/` (`artifacts.py` converts, `cdn.py` uploads through the `enacit4r-files` library, `process_sem.py` is the lab's algorithm); `data/precompute_sem.py` only walks the data repo, so the submission pipeline can call the same functions later.
2. Create the symlink **once**: `ln -s ../../../resslab-hub-data/material/ductile_fracture/sem/_webp frontend/public/sem`. It's gitignored (it would be a dangling link inside the Docker build context and break the prod build). Vite serves the files at `/sem/<id>/...`. `.env.development` already sets `VITE_SEM_CDN_BASE_URL=/sem`, so `pnpm run dev` hits the local files. Production builds use `.env.production` → the real CDN.

For real CDN uploads, drop `DRY_RUN` and put the seven `S3_*` settings in `secrets/.env` (the ENAC names, same as the other ENAC apps' ConfigMaps; values from EPFL ops). The script then sets `has_sem=yes` in `ductile_fracture.csv` for the processed specimens (set-only, never clears) — commit that change to the data repo.

### Ductile-fracture specimen figures

Two different things, both committed under `frontend/public/img/ductile-fracture/`:

- `cnt.png` / `gp.png` — annotated sketches of the two specimen geometries (issue #238), shown inside the tooltip when hovering a specimen type on the dashboard treemap. The connection-type sketches work the same way; both go through `SingleChart`'s `imageFor` prop, which switches its ECharts tooltip to an HTML formatter that appends the figure (`buildFigureTooltipFormatter` in `components/commons/charts/utils.ts`). Putting the figure in the tooltip rather than under the chart is deliberate: the old version pushed the card taller on every hover and had to force one aspect ratio onto figures that don't share one. The tooltip is placed by hand (`buildFigureTooltipPosition`) on the offset/flip/shift rules Floating UI uses — beside the pointer, flipped to its other side when the window has no room, slid back into view vertically. Don't swap that for ECharts' `confine`: it clamps to the _chart_, so a figure taller than the cell gets pinned to the cell's corner and buries the chart. The tooltip's chrome (square, hairline, Suisse, no shadow) lives in `plugins/echarts-theme.ts` rather than the component, since a tooltip is raw DOM hung outside the chart where the square-corner and no-shadow rules in `assets/styles/vuetify-overrides.css` never reach it.
- `figures/<id>.svg`: a drawing of each specimen's own geometry, scaled from its nominal dimensions, shown in the detail drawer. Generated by `cd backend && make precompute-fracture-figures` (needs `RESSLAB_DATA_DIR`), ported from andskia's notebook into `backend/data/fracture_figures_lib.py`. **Commit the output**: unlike the SEM rasters these are a few kB of vector line work each, so there is no CDN in the loop. Rerun after the data repo adds specimens or changes dimensions; the output is deterministic, so an unchanged row rewrites byte-identically and shows no diff. A specimen with no committed figure falls back to its geometry sketch, then to the generic placeholder.

### Adding a new component tab

See `docs/adding-a-new-tab.md` for the exhaustive end-to-end playbook (data repo → backend codegen/router/uploader/migration → OpenAPI regen → frontend views/components/charts/utils/i18n/map/home + contribution, curation and field groups + gotchas from EBF's post-launch feedback). `docs/README.md` indexes every guide: `whats-new-in-2.0.md` (the refactor versus the old app on `main`), `contributing-data.md`, `curation.md`, `dashboard-architecture.md`, `design-system.md`, `sem-images.md`, `auth.md`, `releasing.md`, `worktree-dev-environment.md`, `variable-categories.md`, `modernization-followups.md`.

**The design system.** Before you write CSS, pick a colour, or build a new screen, read `docs/design-system.md` and follow its rules of thumb: write the semantic decisions (`--bg`, `--fg`, `--border`, `--primary`, the five `--title-*` roles), never a raw `--epfl-*` option or a hex; style a new page in its own `<style scoped>`; sentence case, square corners, hairlines instead of shadows, red reserved for the primary action. Two Claude Design projects relate to it: "EPFL Design System" is the heritage (the handoff screens were drawn on it; the export sits untracked in the sibling checkout `../resslab-hub-redesign/design_handoff_resslab_hub/`), and "RESSLab Hub - Design System" is a mirror extracted from this code (tokens, title roles, ECharts theme, an app UI kit with the production class names) for drawing mocks and new screens with the brand. The code is the source: when a token changes here, re-sync that project with the `DesignSync` tool. The guide lists where the app departs from the heritage and where the mirror is ahead. The tokens live in `assets/styles/epfl-tokens.css`. `assets/styles/index.css` is the only sheet `main.ts` imports; it declares `@layer vuetify, tokens, base, overrides, app` and pulls in the others. Vuetify is layered too (`$layers` in `src/settings.scss`, `theme.layers` in `plugins/vuetify.ts`), so a plain selector beats it and `!important` is almost never needed; a component's own `<style>` is unlayered and beats every layer, on purpose. The same brand value is written in three places (token, Vuetify theme, ECharts theme) because canvas and Vuetify cannot read a `var()`; `plugins/__tests__/designTokens.spec.ts` fails if they drift.

**Chart colors for categorical fields** come from `frontend/src/utils/categoryColors.ts`, never from a chart's own ordering: `useDataset(...).colorFor(field)` hands out the Okabe–Ito slots once per field, by frequency in the unfiltered dataset (ties alphabetical), so a value keeps its color when filters reshuffle the ranking and the treemap, stacked histogram and brush overview all agree. Values past the 8 slots repeat the palette muted toward grey. To pin a value whose color people have learnt (a data upload can reorder the frequencies), add it to `CATEGORY_COLOR_OVERRIDES` keyed `'<dataset key>:<field>'`.

**Adding a column to a data dictionary** also means giving it a scientific category, which is what the collapsible groups in the filter rail, the contribution editor, the curation review panel and the specimen drawer are built from. The categories live in the `group` column of each `*_data_dictionary.csv` (resslab-hub-data#46) and are mirrored by `frontend/src/utils/fieldGroups.ts`, whose `groupFor()` prefers the dictionary when it carries one. Review tables: `docs/variable-categories.md`. Most new columns are matched by an existing pattern (`uvc_*`, `pid_*`, `chemical_composition_*`, `_100fit`) and need no edit; anything unmatched lands in `other` and fails `fieldGroups.spec.ts`, which reads the real column list from `database-columns.json` at the repo root. That file is written from the ORM models by `make api` (and `make generate-model`), and `backend/tests/test_database_columns.py` fails when it is stale, so commit it with the model change.

## Conventions

- **Git hooks**: [Lefthook](https://lefthook.dev) orchestrates `commit-msg` / `pre-commit` / `pre-push`. Config in `lefthook.yml` at the repo root; installed automatically by `make install` (or `make hooks`). Escape hatch: `LEFTHOOK=0 git commit ...`.
- **Commits**: Conventional Commits enforced by commitlint on `commit-msg`; Release Please auto-manages versioning.
- **Python formatting**: ruff (lint, `E W F I` rules) + ruff-format via the Python `pre-commit` framework (`backend/.pre-commit-config.yaml`) — staged files at commit time, all files at push time and in CI.
- **Frontend formatting**: ESLint (Vue3 + TS + Prettier) + Prettier on staged files at commit time. `vue-tsc` type-check at push time and in CI.
- **TypeScript**: strict mode; Prettier for formatting.
